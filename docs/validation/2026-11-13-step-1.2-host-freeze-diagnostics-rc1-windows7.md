## Selection, cached state and Escape

All 27 selected phases establish selection flags 7, then observe flags 0 after
the single C dispatch and before releasing the agent. No Escape occurs in that
held interval. The agent still reports cached frozen state when released, then
its normal unfreeze sends WM_CHAR Escape. Agent transitions and host entry/return
timestamps bind that Escape to the release in every selected phase.

All nine selected pending reads remain pending without a control event. After
release, recovery Enter returns only CRLF. Both positive controls in each
same-fixture bracket deliver correctly. This makes a fixed inherited ignore
setting an inadequate explanation for those contrasts.

I can now observe the suspected Windows 7 sequence directly: C clears selection
without delivering cancellation, and the cached state causes a later Escape.
The empty recovery line is consistent with that Escape clearing the old text.
I cannot assign the text loss exclusively to Escape because this experiment
does not observe the cooked input buffer between C and Escape. That distinction
needs a separate control if a later fix depends on repairing this state rather
than preventing the collision.

WOLF's candidate run retained active selection until release, so it did not
establish this Windows 7 sequence. After release, normal scraping can establish
new selection again; a later flags-7 sample does not undo the earlier flags-0
observation inside the held interval.

## A natural race despite the delay control

LEOPARD's third execution position, completed-read delay control, retains the
completed text but misses its event in both the original and extra observation
windows. Its early condition sample sees selection 7; the closer controller
sample sees 0. The subsequent host trace records:

| Event | QPC, frequency 10,000,000 |
| --- | ---: |
| SelectAll returns | 2178515995 |
| C enters | 2178517104 |
| C returns | 2178517327 |
| Escape enters | 2178522570 |

C enters about 0.111 ms after SelectAll returns, within the agent's recorded
freeze. Escape follows about 0.547 ms after C entry. Output and resize later
resume successfully. The [failed-request index](results/step-1.2/host-freeze-diagnostics-rc1/windows7/failed-dispatches.json)
retains the surrounding host and agent events.

This demonstrates why a selection query followed by C, or a delay alone, cannot
provide the required exclusion. Selection can begin after the query. The agent's
acknowledged coordination interval addresses that race in the focused cases.

## Recorder limit and next work

All nine experiment neighbors lose an early trace prefix: 42,248 host-window
events and 84,474 agent events in total. The fixed rings disclose every loss.
The neighbor waits for parent commands and drains these recorders only at close;
the longer Windows 7 suites exceed the 4,096-event capacity. The eighteen coverage
notes all concern these neighboring recorders. Core reviews and focused sessions
have no reported coverage gap.

The neighbor's pending read, zero-event checks, final BRAVO_KEEP input, cleanup
and desktop identity still pass. I cannot claim a complete neighboring window
message or agent history. I need periodic draining before using that history
as a full cross-session regression guard.

My next step is a coordinated H3 research prototype covering the existing native
and shell cancellation paths, together with that recorder repair. It must retain
unchanged controls, original deadlines, single dispatch, modifier restoration,
unknown-outcome handling and no retry after a missing acknowledgment. Completion/
close races, actual access denial, active-child and PowerShell 7 guards still
need their planned qualification. The production runtime remains unchanged;
H3, H4 and VT7 integration remain open.
