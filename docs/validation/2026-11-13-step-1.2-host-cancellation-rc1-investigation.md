# H3 rc1 cancellation failure investigation

Date: 2026-11-13.

I've compared each failure with passing requests, reviewed the dispatch and
fixture code, and run six more repetitions of the unchanged package on WOLF.
The cause is still unconfirmed. The evidence points to a gap between the
acknowledged key-message operation and its read/control-event effects.
I need a diagnostic experiment on Windows 7 before choosing a fix.

The [target review](2026-11-13-step-1.2-host-cancellation-rc1-windows7.md)
still stands: four passing repetitions, five failing repetitions, H3 not accepted.

## What the comparisons establish

The [reproducible comparison](results/step-1.2/host-cancellation-rc1/investigation/comparison.json)
covers all 108 target case runs and 88 accepted Cancel requests. It associates
each request with its containing case's outcome; it does not invent event timing.

All accepted Cancel requests on a given machine have identical Before, During
and After keyboard tables. That includes the failed requests and successful
requests in the same case. The byte values differ between machines, but there
is only one observed table combination per machine.

| Failed request | Passing requests on that machine with identical tables | Of those, same case |
| --- | ---: | ---: |
| NESSY, repetition 2, completed-before-cancel | 29 | 2 |
| TURTLE, repetition 1, powershell-empty | 28 | 1 |
| TURTLE, repetition 3, powershell-empty | 28 | 1 |
| LEOPARD, repetition 2, cmd-empty | 26 | 2 |
| LEOPARD, repetition 3, cooked-repeated | 26 | 6 |

A static modifier-table difference therefore does not separate pass from fail.
This does not prove which key state the host reads later inside its window
procedure: rc1 samples before the nested send and after restoration, not there.

TURTLE's three powershell-empty VT streams are also identical after removing
only title timestamps and replacing their per-repetition path component.
All other VT bytes are preserved in that comparison. One case passes and two
fail because the fixture handler counts differ. Screen output cannot identify
successful event delivery in this example.

The failures are not confined to PowerShell or empty input. LEOPARD's failing
cooked-read case had echoed its unique H3_DISCARD_1 text and recorded a pending
read before cancellation. The read remains pending afterward with no event.
Recovery returns only CRLF; that suggests the old text was removed, but it
does not establish successful read cancellation or explain how the text vanished.

NESSY's failing case has already completed its read, while no-pending-read
passes in all nine target repetitions. Read readiness alone cannot explain
the full failure set. Native fixture failures also prevent attributing the
problem solely to PowerShell, PSReadLine or PowerShell 2.0.

## Where the current observations stop

| Boundary | What rc1 records | What remains unknown |
| --- | --- | --- |
| Session and request | Verified host/thread/HWND, nonce, sequence, lifetime and actual callback desktop | No failed identity or protocol check explains these requests |
| Temporary keyboard state | Exact 256-byte table readback and Ctrl state before SendMessage | State at nested key-message entry and during host processing |
| Key-message send | One synchronous SendMessage call returns; Sent becomes 1 | Actual processing branch, message result and internal event/read decisions |
| Fixture read | Final BOOL, error, text, read index and pending/returned state | Entry/return times and a continuous timeline around dispatch |
| Fixture handler | Interlocked cumulative count and last event type | Handler entry/exit times and whether an event arrives after the recorded observation window |
| Shell prompt | Parsed row, raw LF count, marker files and later usable shell | A new read/prompt generation tied to this cancellation |

[SendMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessage)
returns a message-specific window-procedure result. In rc1, Sent means the
call returned, not that an application received CTRL_C_EVENT. The nested
WM_KEYDOWN is not traced by the existing callback, which handles WM_NULL.

[GetKeyboardState](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeyboardstate)
describes the calling thread's input-state table. A matching pre-send sample
cannot establish every later state read.
[HandlerRoutine](https://learn.microsoft.com/en-us/windows/console/handlerroutine)
runs on a separate thread, so delivery and observation must be distinguished.

## Harness and reference-code findings

I've identified three measurement weaknesses, without treating them as an
explanation for every failure:

- The fixture writes HOST_INPUT> before creating its reader thread. Empty
  startRead checks can find an older copy of that marker elsewhere on screen.
  A created thread and ReadReturned 0 do not prove entry into ReadConsoleW.
  The failed nonempty LEOPARD read has the stronger unique-echo barrier.
- The shell identity command writes its file before its new prompt is
  necessarily scraped. The current atPrompt check can see an older prompt;
  the following LF-count check can include delayed command output or wrapping.
  This is a possible observation race, not proof that it occurred on TURTLE.
- The harness saves final snapshots after bounded polling and settling, not
  timestamped transitions. Increasing a sleep or timeout would not locate
  the failure and must not become the proposed fix without new evidence.

The fixture counter uses Interlocked operations and is not reset during a
session. Each failed packet is bound to the correct retained fixture. I found
no counter-reset or packet-identity error that explains the zero counts.

The agent explicitly restores Ctrl+C processing before registering its own
handler, but does not check those two API return values. The fixture checks
registration of its custom handler but does not explicitly reset the inherited
ignore attribute. This is a diagnostic gap, not evidence that the attribute is
wrong. [SetConsoleCtrlHandler](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler)
documents that the ignore attribute is inherited and handler lists are local
to each process. A shell's own handler list does not by itself suppress the
fixture's handler.

The raw-input guard passes through the released runtime's input transport;
it does not invoke the H3 Cancel key-message operation. Its passes do not
prove how that operation is decoded in raw mode.

I read VT7's reference console code and checked the corresponding modern
[Microsoft key-processing source](https://github.com/microsoft/terminal/blob/main/src/interactivity/win32/windowio.cpp),
[control-event code](https://github.com/microsoft/terminal/blob/main/src/host/input.cpp)
and [unlock path](https://github.com/microsoft/terminal/blob/main/src/host/handle.cpp).
They distinguish window-message filtering, processed-key handling, read
termination and later control-event processing. Selection, scrolling, composition
and dialog state can intercept input before generic processing. These suggest
measurements to make; they are not Windows 7 conhost source or proof of its
failure path. Exact reference revisions and hashes are in
[source-references.json](results/step-1.2/host-cancellation-rc1/investigation/source-references.json).

## Diagnostic experiment before a fix decision

I'll preserve the issued rc1 as the control and use a separate identified
diagnostic build on the same Windows 7 machines. Instrumentation can change
timing, so original and traced trials need to be interleaved and retain their
individual outcomes. A traced pass cannot replace an original failure.

The experiment should keep the same single key-message operation and add:

| Measurement | Question it separates |
| --- | --- |
| Bounded pre/post trace for the nested WM_KEYDOWN, correlated to the existing request | Does the expected window/thread see the key with Ctrl still set, and does it return before restoration? |
| Message parameters, return value, keyboard layout and sampled key state | Is the key interpreted with the intended identity and modifiers at dispatch? |
| Fixture read-entry/return and handler-entry/exit timestamps, monotonic counters and final observations | Is delivery missing, late, or observed before a read transition? |
| Input mode, input-record count and GetConsoleSelectionInfo from the owned fixture before/after the request | Is processed input or selection state changing around the operation? |
| Distinct shell prompt generations and output positions | Is the observation tied to this cancellation rather than an older prompt or delayed identity-command output? |
| A separate controlled raw-reader case using the H3 key-message operation | Which key/modifier record does the host produce without processed-input cancellation? |

Read-entry timestamps still do not prove a read is blocked; retain the unique
echo barrier where applicable and label weaker observations accurately.
Keep original deadline failures even when a later diagnostic window observes
completion. Record never-observed separately from late delivery.

Tracing must use fixed bounded storage, avoid blocking IPC or file I/O in the
host key-processing path, and retain session/lifetime verification. There must
be no queue pumping, private offsets, host patches, foreground input, retries
or appended control events. The
[selection query](https://learn.microsoft.com/en-us/windows/console/getconsoleselectioninfo)
is available on Windows 7 and should observe the owned fixture's console,
without changing selection or input mode.

If key state is lost at nested dispatch, investigate that boundary. If key
state is correct but mode/selection changes intercept the key, investigate that
state transition. If the handler arrives late, investigate delivery and
deadline semantics. If these observations still show correct inputs without
the required effects, reevaluate the host mechanism with that evidence.
None of those fix paths is selected yet. H3 and H4 remain open.
