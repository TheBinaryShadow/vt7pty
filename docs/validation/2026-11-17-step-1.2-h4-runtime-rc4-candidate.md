## What rc4 adds

The core runtime inventory remains 41 cases, or 33 on LEOPARD. I added explicit
desktop preflights and cause-specific missing/wrong-module checks.

Seven separate cases cover inactive-desktop refusal, eight live sessions and
caller resources, explicit-breakaway-allowed and silent-breakaway enclosing jobs,
timeout before dispatch, timeout during the callback and agent death during the
callback. The external test gate observes the retained host thread and keyboard
state. It adds no product fault switches.

The resource case keeps eight hosts and pending clients alive together, then
sequences cancellation and resize work so the bounded diagnostic channel retains
every snapshot. I do not count it as eight simultaneous callback dispatches.

The new 120-minute opt-in soak keeps an active session and a pending neighbor,
cancels and checks exact next reads, resizes, and periodically recreates sessions.
Rolling fixture observations must retain continuous event-sequence coverage.
The existing baseline regression soak remains a separate target-machine phase.

I also added guided US/Croatian physical input, lock/unlock and elevated-caller
checks. The [runtime guide](../H4_RUNTIME.md) and
[manual instructions](../H4_MANUAL_CHECKS.md) describe the collection.

## Preserved interruptions and refinements

My first full rc4 collection stopped at cycle 457 when Windows denied access to
the input desktop with error 5. I confirmed that WOLF had locked or changed
desktops. The prior 456 cycles, 503 keyboard restorations and 46 recreated-session
exits were independently verified. That run remains failed and does not count
as a two-hour pass.

The primary and neighbor lifetime files were not written on that exception
path. Later observations showed both original host identities had exited; those
observations do not replace the missing lifecycle records. I reran the entire
unchanged collection after returning to the ordinary desktop.

I also retained the unissued rc3 collection and earlier internal experiments.
Those caught a fixture-schema mismatch, a raw-read handler expectation, loss on
the bounded diagnostic channel, cold-start resource measurement, and a stale
timeout-marker risk under PID reuse. The timeout monitor now starts at a recorded
log byte offset before the current request. Developer review also accepts a
child failure logged before the parent's process-creation record while requiring
the precise module failure cause.

A documentation correction during the first rc4 rebuild changed the source
identity. Verification rejected that build. I restarted from the frozen commit;
the issued archive comes from that clean build.
