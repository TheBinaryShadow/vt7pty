## Mechanism observations

Both probes establish a pending cooked ReadConsoleW call after the echoed
PROBE_TYPED barrier. They then distinguish API return, control-handler delivery
and read completion. Input mode is 135 on every target.

| Observation | READCONSOLE_RECORD_EVENT | READCONSOLE_OWNED_CANCEL |
| --- | --- | --- |
| API result | WriteConsoleInputW succeeds, error 0, two records written | CancelSynchronousIo returns FALSE, error 1168 (ERROR_NOT_FOUND) |
| Control delivery | Exactly one CTRL_C_EVENT | Exactly one CTRL_C_EVENT |
| Pending read within cancellation deadline | Remains pending | Remains pending |
| Text returned after boundary Enter | PROBE_TYPED, character 0x03, CRLF | PROBE_TYPED, CRLF |
| Subsequent read check | Not part of this recipe | NEXT_PROBE plus CRLF returned normally after boundary recovery |
| Final fixture completion | Final marker, exit 37, cleanup | Final marker, exit 37, cleanup |
| Overall result | Fail on all three targets | Fail on all three targets |

The record-based approach inserts character 0x03 into the retained line rather
than canceling it. Combining those records with the separate event therefore
does not meet the cancellation contract.

Direct cancellation finds no matching cancellable I/O request, even though
the fixture's read is demonstrably pending. The event still reaches the handler
and leaves the typed line intact. Boundary Enter completes that original read;
only then does the explicitly requested second read return NEXT_PROBE normally.
That recovery does not make cancellation successful.

This differs from the development-host observation: WOLF's first cancellation
returned zero text with error 995, then lost the following line. On Windows 7
the initial cancellation attempt itself fails, and the second read works after
ordinary Enter recovery. These are separate measured behaviors; the WOLF result
cannot qualify or describe the Windows 7 mechanism.

The observations reject these two recipes for the tested pending ReadConsoleW
call. They do not establish that every user-mode route, console read API or
input mode is impossible to support.

## Preserved guards and existing failures

Every applicable active-child case still passes: nine on NESSY, nine on TURTLE,
six on LEOPARD, 24 observations in total. Handled processed Ctrl+C arrives once;
default-handler termination retains native status 0xC000013A; unprocessed
Ctrl+C and z arrive as ordered key records without a control event. Each parent
shell remains usable and executes the next command.

PowerShell 7 prompt cancellation passes on A/B. Controlled Unicode and resize
continue to pass on all targets. The six original failures remain: CMD_EMPTY,
CMD_PARTIAL, PS_EMPTY, PS_PARTIAL, READCONSOLE_TRANSPORT and READCONSOLE_EVENT.
The two new mechanism failures raise each target's total from six to eight
without changing any original result.

Both partial prompt cases still execute the canceled command after boundary
Enter: cancelled-command.txt contains BAD. The independent next-command marker
contains CONTINUE, and both shells remain alive. Retained usability alone
does not satisfy cancellation.

## What I concluded and next design

The public-API mechanism measurement gate is complete. Neither measured
approach is a production candidate. The released runtime, native platform floor,
API and protocol remain unchanged; KB3191566 is not made a runtime requirement.

My next step at this point was a bounded user-mode console-host cancellation
design: establish the identity and ownership of one session's actual host,
determine how to request read cancellation within that host, and define
acknowledgment, failure and isolation behavior. The earlier HWND/thread-hook
experiment was rejected before installation and remains unqualified research.
Do not revive it as a supported fix based on these API results.

An application-facing read shim remains a separate alternative requiring an
explicit launch/load boundary and read-semantics design. No host hook, injected
application shim or driver was implemented by this evidence review.

A later prototype must discard the old line, preserve the next read/command,
deliver one appropriate event, preserve unprocessed keys and active-child
behavior, and keep sessions isolated. It needs its own source identity and
target evidence before a distinct runtime candidate is issued. Step 1.2,
broader Step 1.1 coverage and Milestone 1 remain open.
