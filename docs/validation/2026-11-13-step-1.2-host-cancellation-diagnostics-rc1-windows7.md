# H3 diagnostics rc1: Windows 7 review

Recorded: 2026-11-13.

I've reviewed all three diagnostic collections. Every collection completed,
including LEOPARD on PowerShell 2.0 without KB3191566. The controls passed six
of nine trials; the traced build passed seven of nine. H3 remains open.

The strongest new evidence is a selection-state correlation: both traced
native delivery failures sampled an active selection immediately before the
key request. The other 87 custom-handler requests sampled no selection and
recorded a handler entry. The agent's screen-scraping freeze uses selection,
which makes coordination between scraping and cancellation the next experiment.
I have not treated this correlation as a confirmed fix.

## What the native traces establish

Across all 107 recorded sends, the nested entry has Ctrl and left Ctrl set,
without Shift or Alt held. Entry and return keyboard tables match the applied
table, and the final restoration matches the original table. Actual host,
thread, HWND and request binding pass the auditor. These observations do not
support lost Ctrl state at the measured boundaries as the explanation.

| Custom-handler requests | Requests | With a handler entry | Without one |
| --- | ---: | ---: | ---: |
| Selection flags 0 before request | 87 | 87 | 0 |
| Selection flags 7 before request | 2 | 0 | 2 |

This comparison excludes nine default-handler exits and nine raw-key cases.
Receipt-only operations have no final key trace and are outside this table.

The two selection-active samples are NESSY's
[second repeated-read request](results/step-1.2/host-cancellation-diagnostics-rc1/windows7/raw/nonesu-20261113-045721-f2d09196/04-trace/native/suite/cooked-repeated/host-7-request.json)
and LEOPARD's
[completed-read request](results/step-1.2/host-cancellation-diagnostics-rc1/windows7/raw/legacy-20261113-045709-3574bcfa/06-trace/native/suite/completed-before-cancel/host-2-request.json).
Both sample flags 7 before dispatch and 0 afterward, with processed input
enabled, successful public queries and the custom handler registered.
Neither records a new handler entry through its final fixture observation,
about 7.65 and 10.35 seconds after key entry respectively. Both additional
five-second windows end with their predicates false.

[Microsoft's selection flags](https://learn.microsoft.com/en-us/windows/console/console-selection-info-str)
identify 7 as an active, nonempty mouse-style selection. This does not establish
that a person used the mouse. The accepted agent source enters SelectAll to
freeze the console, then sends Escape to unfreeze it. Its Windows 7 scraper
uses that freeze while reading the buffer. The separate research controller
dispatches cancellation without sharing the agent's freeze state. Exact source
snapshots and revisions are in
[source references](results/step-1.2/host-cancellation-diagnostics-rc1/windows7/source-references.json).

My leading explanation is that a key can reach the console while the scraper's
selection is active and be consumed by selection handling. Modern VT7 reference
code handles selection before ordinary key processing, which supports examining
that boundary but does not prove Windows 7's internal branch. Selection is
sampled in another process, about 0.19 and 0.31 ms before nested entry in these
failures, not atomically inside the key handler. The trace does not identify
the exact selection transition or prove which process caused it.

The raw host-key case passes on all nine traces: virtual key C, scan code 46,
left Ctrl modifier 8, character zero and no control event with processed input
disabled. Character zero here is preserved data, not evidence of lost Ctrl.

## Separate shell-observation finding

LEOPARD's failed CMD workflow has one event, a fresh prompt and no canceled
command file. Its continued-command file ultimately contains CONTINUE plus
CRLF, while NextCommand is false. This resembles the retained WOLF control
failure. The harness accepts file existence plus a prompt before reading the
file content; an older prompt and a newly created but unfinished file can
satisfy that barrier. The records do not timestamp that file read, so I cannot
claim this exact race is proven. It needs a complete-content barrier and a
prompt observation tied to the command being checked.

PowerShell's counters also retain ambiguity: three TURTLE empty-input traces
record generation 1 before cancellation and 2 at the deadline. The identity
command itself can produce generation 2. The counter alone cannot attribute
that prompt to cancellation, although these traced cases do record their event.

## Next decision

I'll use a controlled experiment to serialize the agent's scrape/freeze/unfreeze
work with one cancellation dispatch on the same owned session. It must retain
the unchanged controls and trace individual outcomes. A caller-side check for
selection followed by an independent send leaves a race; blindly sending Escape,
retrying Ctrl+C or appending a generated event can change input or duplicate
delivery. None is selected as a fix here.

I'll tighten the shell marker/prompt observations separately and preserve the
old failures. This review adds evidence for the next H3 experiment; it does not
accept H3, H4, ordinary-desktop production use or VT7 integration. No runtime
or cancellation implementation changed during review.
