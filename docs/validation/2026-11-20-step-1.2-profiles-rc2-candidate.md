## Why rc1 was superseded

The [prepared rc1](2026-11-19-step-1.2-profiles-rc1-candidate.md) starts correctly
from a fresh extraction path after the WOLF sign-in. Its frozen guards pass
41/41 and input controls pass 43/43, but one of twelve profile cases fails at
history recall. The command actually runs. Its second JSON proof remains
unpublished because the harness holds the old file open without delete sharing;
PowerShell records an IOException during replacement.

I changed only the profile reader to permit shared read/write/delete access.
This permits replacement while a read handle remains open, as Microsoft
documents for [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
and [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
The bounded reader still checks complete data, session identity and the actual
invocation counter. I added no retries of application commands.

The new deterministic check holds the original stream reader open and
reproduces error 32. With the corrected reader still held open, replacement
succeeds, the retained handle sees the old proof, and the next reader sees the
new proof. Every profile trial runs this check on its own result files.
The existing H4 reader and frozen controls stay unchanged.

I retain rc1's original ZIP, failed collection and independent rejection.
Rc1's SHA-256 remains
95c91bc9efaba6752d7406a5b7665ef847c2db50c4cd7ffbce3ad6aa192f8031.
The fresh-session contrast supports the earlier path-dependent hook observation;
it does not establish that issue's underlying Windows cause.
