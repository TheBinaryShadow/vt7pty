# Cancellation research reassessment

Recorded: 2026-11-13.

I still recommend investigating coordination between the scraper and cancellation.
The historical research and an independent recheck of the collected evidence
support that direction. I would strengthen the experiment before building it:
measure the freeze and Escape traffic, deliberately control selection state,
and compare the conditions within the same instrumented build.

A coordinated build producing more passing runs would not, by itself, prove
the cause. Instrumentation, additional handshakes and stronger shell checks all
change timing. The next experiment needs to distinguish those effects from
excluding a selection freeze at dispatch.

## Evidence reconsidered

I reviewed the accepted 0.5.0 release record and the fidelity, public-API,
identity, dispatch, cancellation and diagnostic investigations. The original
release's 30-case suite and three 120-minute soaks establish its bounded
baseline. The later cooked-read and shell tests expose behavior beyond that
original contract; their failures remain recorded.

| Evidence | What still follows from it |
| --- | --- |
| Initial and rc3 fidelity baselines | Classic CMD/PowerShell cancellation fails; handled/default active-child interruption and the existing unprocessed transport pass their applicable guards |
| Cooked-read transport and direct event probes | One handler event can arrive while ReadConsoleW remains pending with its old text |
| Record-plus-event probe | Injected character 0x03 remains in the line; it does not cancel the read |
| CancelSynchronousIo probe | Windows 7 returns error 1168 and leaves the read pending; WOLF's different first-read result does not qualify this mechanism |
| H1 and H2 | Actual host identity, callback execution and isolation are established for the measured configurations; they do not establish cancellation |
| Original H3 target runs | 103/108 cases pass, with five missing-event failures; matching modifier snapshots do not distinguish those failures |
| Paired diagnostic target runs | 219/225 cases pass; both traced native delivery failures sample selection before dispatch, with measured Ctrl state intact |

The independent hash recheck covers eight inventories and **7,229 references**,
with no missing files, byte-length differences or SHA-256 mismatches. This is a
count of inventory references, not deduplicated files. The
[recheck record](results/step-1.2/host-cancellation-diagnostics-rc1/reassessment/historical-inventory-recheck.json)
names each scope; its preserved script makes the check reproducible. No native
test or Windows 7 machine was rerun for this reassessment.

The latest relation was also recomputed directly from request packets and
fixture timelines: 87 custom-handler sends with pre-request selection flags 0
have a later handler entry; two with flags 7 have none. Those two public samples
end 0.1852 ms and 0.3067 ms before nested key entry. They are close observations,
not atomic measurements inside the Windows 7 key handler. The
[paired review](2026-11-13-step-1.2-host-cancellation-diagnostics-rc1-windows7.md)
retains the full case-level findings and their limits.

I do not infer Windows 7's exact copy behavior from modern ConPTY code.
[Microsoft's 2014 console announcement](https://blogs.windows.com/windowsdeveloper/2014/10/07/console-improvements-in-the-windows-10-technical-preview/)
introduces the newer Ctrl+C copy/cancel behavior as a Windows 10 change.
Selection consumption is the hypothesis to test on Windows 7; copying to the
clipboard is not established by our traces. ReactOS also filters non-WM_KEYDOWN
messages in its selection branch, so it cannot establish the behavior of our
agent's WM_CHAR Escape. That transition must be measured on the target systems.

The common advice to disable QuickEdit does not resolve the measured case.
Both native failures use input mode 135, or 0x87, already excluding QuickEdit
0x40 and mouse input 0x10. The fixture sets extended flags explicitly. The agent
still invokes SelectAll directly. [SetConsoleMode](https://learn.microsoft.com/en-us/windows/console/setconsolemode)
documents the input flags; the programmatic selection comes from our source.

## Additional interaction to measure

The agent's Win32Console::m_frozen is a cached Boolean. Entering a freeze sends
SelectAll and sets it true. Leaving that believed state sends WM_CHAR Escape
and sets it false. FreezeGuard restores the cached prior state, rather than
reconciling it with actual selection.

That creates a plausible sequence needing direct observation:

1. The scraper selects the console contents and believes it is frozen.
2. H3 sends one Ctrl+C, which may clear selection without delivering an event.
3. The agent still believes it is frozen and sends its normal unfreeze Escape.
4. That Escape may now reach a cooked read and clear text without aborting it.

This could connect missing events with the earlier recovery reads returning
only CRLF. It is not proven: the current recorder follows C but does not retain
all SelectAll/Mark/Escape traffic. I will not turn this sequence into an assumed
diagnosis or append Escape as a cancellation fix.

## Refined experiment

Retain the exact issued rc1 control and the existing unsynchronized trace
condition. Use the same new instrumented build for the causal contrasts below.
Begin with the already-completed-read case, then pending reads with a unique
echo barrier. This tests both observed native failure contexts without making
an empty-read marker the only readiness evidence.

| Condition | Controlled state | Question |
| --- | --- | --- |
| Selection-free reference | Agent completes its freeze/unfreeze work and holds a bounded quiescent interval | Does one C dispatch deliver the expected event and read outcome? |
| Selection-active challenge | The owned agent deliberately establishes selection across one C dispatch | Is the key consumed or does delivery still occur? What clears selection? |
| Coordinated normal operation | Agent excludes scrape and resize freezes around one dispatch, then resumes normal work | Does exclusion preserve cancellation, subsequent input and output under activity? |
| Comparable-delay control | Similar trace/handshake delay, with ordinary freeze scheduling retained | Is a changed outcome explained by exclusion rather than extra delay alone? |

Use positive delivery controls before and after the selection challenge in the
same fixture where appropriate, and fresh fixtures where prior input could
contaminate a contrast. NESSY already handles its first cancellation before
missing its second; a fixed inherited ignore setting alone cannot explain that
sequence. Preserve individual outcomes and rotate condition order rather than
repeating failures until they pass.

The recorder should correlate these observations with the existing request ID,
host/session identity and read/handler clocks:

- Agent scrape/resize and freeze begin/end, freeze generation and cached state.
- Host entry/return for SelectAll, Mark and WM_CHAR Escape, alongside the C key.
- Public selection snapshots from the owned fixture, with their observation intervals.
- Exactly one key operation, modifier restoration, handler/read transitions,
  subsequent input and resumed output.

Keep fixed bounded storage and no blocking IPC or file I/O in host-message
recording. Do not call console-query APIs inside conhost to infer a fixture's
console selection. Negotiate quiescence before entering the host callback,
after the agent's existing freeze scope has unwound. Cover resizing as well as
periodic scraping; do not suspend the agent thread or stop it inside a console API.

A callback waiting for the agent can deadlock if the agent is already waiting
for that host's synchronous message. [SendMessage](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessage)
also permits incoming nonqueued-message processing while the sender waits.
The test needs a bounded gate, an explicit resume path and retained
unknown-outcome handling, without retries or additional control events.

## Keep shell measurements separate

The CMD usability failure remains an observation problem to investigate:
the expected file contents exist afterward, but the harness reads once as soon
as file existence plus a recognized prompt passes. The prepared CMD token is
session-specific, not a new token for every command. PowerShell's recorded
generation does not currently constrain that predicate either.

Use complete expected content and a command-specific prompt/generation barrier,
and record first existence versus first complete content. Apply those same
measurement changes to every experimental condition. Do not count improved
shell observations as proof of a cancellation fix, or a prompt as proof that
the shell is blocked in ReadConsole.

## Decision and stopping criteria

My recommendation remains the coordination experiment, with these refinements.
If held selection consistently prevents delivery and the verified selection-free
condition restores it, the message timeline can establish a causal boundary.
If selection-active dispatch still delivers reliably, or coordinated dispatch
still loses events with no intervening freeze, revise the explanation rather
than widening timeouts or adding another Ctrl+C.

Keep the existing unprocessed input path and its character 0x03 behavior. After
the native contrast, require the existing active-child/default-handler, next-read,
isolation, output/resize and PowerShell 7 guards before a production candidate.
H3 and H4 remain open. This reassessment changes no runtime, test implementation
or candidate package.
