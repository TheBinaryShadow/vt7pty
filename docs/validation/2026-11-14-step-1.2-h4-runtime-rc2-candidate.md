## Why the archive is still held

All nine extracted-package trials collected their original outcomes. The new
runtime and frozen reference failed during startup at their new paths. The
runtime trace records SetWindowsHookEx failure 126 after the DLL loaded and its
callback export was found.

I reproduced the distinction without targeting a host: loading the same DLL
bytes and installing a hook on my test process's own thread succeeds at an
existing registered path and fails with 126 at new paths. The frozen reference
DLL shows the same contrast. This rules out a different payload as the cause
of this particular comparison.

A retired Microsoft debugging post by Alejandro Campos Magencio describes
a shared limit of 32 distinct global-hook DLL names/paths on systems including
Windows 7. The [preserved Microsoft post](https://www.sysadmins.lv/retired-msft-blogs/alejacma/setwindowshookex-fails-with-error-errormodnotfound.aspx)
identifies its original author, date and MSDN URL. My thread-scoped tests show
a related registration failure on Windows 10, but I have not measured the
current limit or proven that it is the cause.

A fresh Windows sign-in on WOLF is the next discriminating check. I will rerun
the unchanged extracted rc2 archive afterward. I have not changed Windows
settings, signed out, rebooted, or weakened the archive acceptance gate.

The [rc2 preservation inventory](results/step-1.2/h4-runtime-rc2/preserved-files.json)
retains the failed collection, build/verification records, successful 41-case

The [followup inventory](results/step-1.2/h4-runtime-rc2-followup/preserved-files.json)
