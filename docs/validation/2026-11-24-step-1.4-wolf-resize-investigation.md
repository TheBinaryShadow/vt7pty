# Step 1.4 WOLF resize investigation

Recorded on 2026-11-24 in Europe/Zagreb.

I repeated the three resize cases on WOLF, Windows 10 build 19044, using the
accepted input rc2 and fixed screen rc2 binaries from the issued ZIP.
The 24 observations separate a viewport offset, native marker reflow and
an intermittent console-host failure. [Issued candidate](2026-11-24-step-1.4-screen-rc2-candidate.md)

## Synchronized resize

All eight controls show native viewport top 1. The cursor is at row 7
relative to that viewport and row 8 in the VT reader. I replayed the
captured stream with the existing reader and compared the shared rows
at both origins. The candidate replay has 42 cell and 10 attribute
differences at the original origin. With the native one-row offset, all
2,900 shared cells and attributes match and the cursor aligns.

The reader keeps the top-left cells when its dimensions change. The
Win32 observation also records the viewport's position within the
buffer. I will capture that position at each resize checkpoint and
compare the stable viewport explicitly. The overlap comparison explains
the offset in this reader. VT7's terminal code reflows its buffer and
tracks the visible top with its own viewport policy.

## CMD and PowerShell restoration

In all 12 completed live rc2 repeats, the primary marker is at column
82, row 0 with attribute 0x1e after return. It starts at column 2,
row 1. The final VT frame matches the native frame, and the shell runs
the next edited command.

I reproduced the same relocation and attribute in a native console on
80-to-100-column growth. The relocation occurs at the buffer resize
after painting all 80 columns, including a trial with a fresh console.
Painting only 79 columns or just the marker leaves it at (2, 1). I will
keep a fixed-row control and check marker content, attributes and the
native reflowed frame in the live cases.

## Console-host loss on shrink

Four of the 16 issued live repeats lost their connection on an 80×25
shrink, twice with each runtime. WOLF recorded four `conhost.exe`
faults in that run window with fast-fail code `0xc0000409` in
`ucrtbase.dll`. The system fault record leaves the internal call site
open. [Microsoft fast-fail documentation](https://learn.microsoft.com/en-us/cpp/intrinsics/fastfail?view=msvc-170)

I compared alternate-buffer resizes in separate native consoles. With
the agent's Select All sequence, five of six trials lost access to the
console. With selection disabled, all six completed. Skipping or delaying
selection after shrink still failed, as did leaving the entire shrink
unfrozen while keeping selection on growth. The native window PID
resolved to the probe process in this environment, so I use those trials
as disconnect evidence and use the WOLF event log for host faults.

I built a scratch agent that skips selection throughout resize in
direct mode on the detected modern console path. With the issued
fixtures it completed all 16 live workflows and all 128 resize
requests. Both shells returned and their native and VT frames matched.
The fixed-position marker check and the synchronized viewport offset
remain visible in that build.

The runtime change to take forward is the modern direct-buffer resize
path across both growth and shrink. I will use fresh geometry from the
resized buffer for the direct scrape and keep the Windows 7 freeze path.
The scratch result guides the next candidate. Step 1.4 remains open
for the corrected WOLF checks and the exact candidate rerun.
